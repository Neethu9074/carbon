## Tool Support: Chromatic

![chromatic-icon](https://user-images.githubusercontent.com/217931/87825964-5cfdf780-c878-11ea-9146-4109fd52cbcd.png) One of the best tools on the market for testing our components.


![image](https://user-images.githubusercontent.com/217931/85304702-56b07180-b4ac-11ea-9869-e33d96055b59.png)

Compared to Storybook, Chromatic is a cloud tool which records and compares Stories to "known good" baseline and
allows teams to do reviews on the changes.

Chromatic integrates nicely with our existing GH workflow together with 📕[Storybook](https://www.notion.so/instana/Storybook-Documenting-the-UI-67e5904862c548728ffd690de4a36e3b)

## Workflow integration - how do I use it?

Compared to normal work, we will have another step at the end of implementation: Review the ~~code~~ UI.

Because it costs money 💰, we **do not want** to run the complete suite on every commit.
Instead, you decide if your work will change some parts of the UI and you want to verify the effect.

1. We create the storybook and upload it to chromatic **only for git branches names** starting with
   * `storybook-` or
   * `chromatic-`

   Example: `chromatic-evaluation`
1. Now you can **work** on UI components and Storybook **as usual**.
1. Run **Storybook locally** at least once and verify
1. Pushing your work triggers usual Jenkins build. This will now automatically **run the UI testing**.
1. It **builds and uploads Storybook** to Chromatic and runs the comparison with known good
    <img width="600" alt="chromatic-build-stats" src="https://user-images.githubusercontent.com/217931/87821107-9120ea80-c86f-11ea-934d-148265c1bdd4.png"/>
1. When you **create a PR** Chromatic also added the **extra check** for any UI changes (if exist) and links to
 the review page in chromatic.
    ![chromatic-pr](https://user-images.githubusercontent.com/217931/87825958-5a9b9d80-c878-11ea-808b-32ddd0cf125c.png)
    1. The PR is 🟡 "pending" as long as there are **open changes** to be reviewed.
    1. If unwanted changes do not get approved, the build will set to 🔴 "failed".
1. While reviewing you can add comments 📝
1. After things got fixed, the full **PR can be approved** in Chromatic.
    _**`xxx`**_
1. When the PR can be merged:
   1. With a **regular merge**, Chromatic can correlate last approved UI version with the commit history.
   1. After squashing or rebasing Chromatic won't be able to track already approved UI changes.
1. After merging the changes into `develop` branch, and creating a new branch on that,
   Chromatic will use this as the baseline for "last known good"
